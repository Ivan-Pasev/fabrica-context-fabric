# FABRICA Context Fabric v0.4.0 — Constitutional KBI Project Cells

**Type:** Technical R&D manuscript / public-safe source projection  
**Phase:** Ω-OV-P04 · 16 October 2026  
**Publication boundary:** source release candidate, not an independently verified scientific theorem, production security certification or live upstream interoperability report.

## Abstract

Long-term research agents need a reliable means to read, propose, verify, and amend an evolving technical corpus across unrelated conversations, models and tool environments. Persistent vector databases can improve recall but do not inherently establish source authority, research claim correctness, permission to edit, or release eligibility. FABRICA Context Fabric (FCF) proposes a four-plane separation of context, authority, evolution and witness. This version implements a project-bound `.kbi` constitutional capsule, derived from two separately sourced KBI lineages: historical *Kernel-Based Intelligence* for bounded reasoning/execution and *Knowledge Boundary Intelligence* for claim/evidence arbitration. Live native Google Drive manuscripts remain authoritative for research; GitHub is intended for public, independently tested code and release tags; OpenViking is an external, version-pinned context substrate. P04 adds a finite DAG of nine kernels, independent evidence states, a source registry, fail-closed promotion contracts and an offline target-project scaffold. Ninety-nine local tests pass, including simulated HTTP tests; no genuine OpenViking runtime or GitHub public release has yet been observed.

## 1. Source-grounded terminology

A previous GILC KBI manuscript describes intelligence organized into bounded kernels, each with domain, routing, constraints, validation and output type. A subsequent Digital Fabrica LIVE KBI profile defines the acronym as *Knowledge Boundary Intelligence* and supplies five assessment outcomes and six distinct evidence properties. The FDF R25 portable-cell proposal already recognized the collision, using namespaced epistemic and operational layers with project-bounded adoption and source primacy. FCF does not assert the two KBI lineages are identical or that any one is a universally ratified external standard. Both represent project-specific research proposals with explicit validation limits.

## 2. Architecture and law

FCF's four proposed planes are:

- `CONTEXT`: addressable resources, memories, derived summaries, and skills; OpenViking v0.5.0 is an external candidate.
- `AUTHORITY`: real user, institution, source/version, capability permissions, privacy constraints and project invariants.
- `EVOLUTION`: reviewable memory proposals, hypotheses, staged diffs, supersession and bounded promotion gates.
- `WITNESS`: source version, byte hashes, tool receipts and independent execution evidence with precise claim boundaries.

The operational kernel records `{id, namespace, class, operation, required_capability, output_type, depends_on, invariants, effect, default_decision}`. It is not a magic sandbox: permission checks must be enforced by the actual connected provider and host runtime. The epistemic assessment associates subject, claim class, sources, evidence properties, dependencies, conflicts, authority scope, evaluator, status and outstanding obligations. Neither output inherently grants an execution permission.

## 3. Evidence semantics

Evidence axes are independently tracked: E0 assertion; E1 resolvable reference; E2 bounded deterministic mechanical validation; E3 independent reproduction; E4 content-addressed evidence; E5 recognized external attestation. They are **not** a single confidence number, truth ladder or proof. Assessment statuses PASS, FAIL, HOLD, UNKNOWN and UNRESOLVED apply to specified predicates. In particular: content hashing can demonstrate byte agreement but not source authenticity or semantic truth; a unit test demonstrates only the behavior exercised in that test; LLM memories are propositions, not automatically accepted facts.

## 4. Canonical folder and continuity contract

The intended operational path in any authorized chat is: read live START_HERE, then native STATE_AND_HANDOFF; inspect the current project constitution, publication/rights boundaries and revision IDs; read the `.kbi` capsule and active White Paper; route the bounded task; stage and validate candidate diffs; request actual authorization; commit native Doc changes with a supported revision guard; verify readback; update handoff last. Cached ZIPs, indexed vectors and chat summaries remain subordinate to live canonical documents. This is a desired discipline; its complete enforcement across all hosts is not claimed.

## 5. Kernel lattice

The current capsule defines a finite prerequisite DAG:

`SENSE → CLASSIFY → ROUTE → SYNTHESIZE/STAGE → REDTEAM → VERIFY → REVIEW → HANDOFF PROPOSAL → RELEASE CANDIDATE`.

SENSE observes live sources; CLASSIFY separates assertions and evidence; ROUTE defines bounded tasks; SYNTHESIZE stages work; REDTEAM tests overreach/contradictions; VERIFY runs applicable mechanical checks; REVIEW requests scoped authorization; subsequent nodes draft handoff and publication candidates. Any role label remains descriptive until actual host capabilities and identity are verified. The DAG is checked for duplicates, invalid references, unknown capabilities and cycles. It does not create an autonomous execution engine.

## 6. Portability mechanism

The Python standard-library `fcf.kbi.scaffold` generates candidate `.kbi` folders for another project using **that project's** explicitly provided ID, Drive root and native START/HANDOFF URLs. It refuses unsafe IDs, non-HTTPS or mismatched URLs, and overwrite of existing destinations. It produces new source IDs, closed gates and unverified claims. Candidate generation causes no Drive or GitHub write. Target adoption additionally requires independent examination of its existing laws, rights, source registry and verified owner/host authority. The portable cell is therefore a *refabrication process*, not a copied super-prompt.

## 7. Evaluation evidence

The local test count is 99: the P03 baseline contained 68 tests, P04 added 25 KBI-specific tests and six target-project-scaffold tests. Three legacy JSON schema specimens and the example scientific conflict case also pass. An isolated ZIP extract was rerun through the checks. The local HTTP integration checks use an emulated server, not the OpenViking binary. No claims about actual production performance, security against all prompt injection, external proof correctness or successful GitHub CI are supported.

## 8. Dual-distribution policy

Google Drive holds native, continuing manuscripts and constitutional research state; public GitHub should hold reviewed, executable code, tests and releases. The local R&D ZIP may include real Drive references for authorized continuity. A separate public-safe ZIP replaces internal Drive identifiers with non-live source placeholders and omits private provider readback metadata. Exporting a public reference package is not identical to publishing a GitHub repository. A public release requires actual repo creation, provider readback, CI and human/maintainer review. OpenViking source remains a distinct AGPL-3.0 codebase and is not embedded in FCF.

## 9. Open validation debt

High-priority unclosed work includes genuine OpenViking v0.5.0 provisioning, real account/ACL isolation and failure recovery, transparent source authenticity, incremental index consistency, rights review, secure private document access, approved tool authentication, license obligations and formal correspondence between manifest laws and host enforcement. The absence of live tests is recorded as HOLD, not inferred success.
